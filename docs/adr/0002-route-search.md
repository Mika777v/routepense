# ADR-0002: 運賃は手で入れたまま、駅すぱあと API のフリープランで経路の URL を付ける

- 状態: 提案（オーナーの確認待ち）
- 日付: 2026-11-02
- 関係: 要件定義の U1（`docs/requirements.md`）、Task #27

## 背景

要件定義の U1 は「理想は『経路検索 → ルート選択 → 金額算出』。運賃を受け取る部分を差し替えやすくしておく。有料 API の要否を調べる」。
今は、ルートの片道運賃を手で入れている（F1）。

このアプリの使い方では、ルートは一度登録すれば、運賃はほとんど変わらない。
経路検索を呼ぶのは「ルートを登録・編集するとき」だけで、**年に数回**の見込み。日々の記録や一括設定では呼ばない。

## 調べた選択肢

2026-11-02 に、公開されている情報（各社の案内ページ・技術記事）で調べた。
クラウドのセッションからは各社の仕様書のサイトに直接つながらなかったため、細かい条件（上限の回数・表示の義務など）は、実装の前に仕様書で確かめる。

| | 経路検索 | 運賃の数値 | 費用 | 申し込み | メモ |
|---|---|---|---|---|---|
| A. 手入力のまま | なし | 手で入れる | 0円 | 不要 | 今の形 |
| B. 駅すぱあと API フリープラン | あり（簡易） | **返らない**。経路結果のページの URL が返る | 0円 | 必要（個人可。キーはメールで3営業日以内） | 路線バスは対象外。技術サポートは無い |
| C. 駅すぱあと API 買い切り・スタンダード | あり | 返る（定期代も） | 5,000件で5,500円〜（買い切り）。スタンダードは従量 | 必要 | 法人向けの案内が中心。評価版は90日無料 |
| D. NAVITIME（RapidAPI） | あり | 返る | フリーミアム（無料枠の中身は未確認） | RapidAPI の登録 | 電車の時刻は実際の時刻表ではなく推定。バスは RapidAPI では使えない |
| E. Google Maps（Routes / Directions API） | 日本の電車の経路は返らないという報告がある | 返るのは全区間の運賃が分かるときだけ | 従量 | 必要 | 日本の対応は公式の表で確かめられなかった |
| F. 公共交通オープンデータ（ODPT） | なし | 一部の事業者の駅間運賃だけ | 0円 | 必要 | 経路探索は自分で作ることになる |

E と F は、日本の電車の通勤経路を調べる目的には足りないので外した。

## 決定

**A（手入力）を基本にし、B（駅すぱあと API フリープラン）で経路結果のページの URL をルートに付けられるようにする。**

- 運賃は今のとおり手で入れる。ルートの登録の画面で、出発駅・到着駅から駅すぱあとの経路結果のページを開けるようにし、それを見ながら運賃を入れる。開いたページの URL はルートに残し、後から確かめられるようにする
- 有料の API（C・D）は使わない。年に数回しか使わないのに、契約や従量の管理が増えるため
- 経路検索は backend の**インターフェースの後ろ**に置く（下の「作り」）。後から C・D に替えて運賃の数値も受け取るときは、実装を1つ足して、組み立ての1か所を差し替えれば済むようにする（U1 の「差し替えやすくしておく」）

## 作り（Task に分けるときの目安）

- `shared`: `Route` に経路の URL（任意の項目。例: `searchUrl?: string`）を足す。記録にコピーする `RouteSnapshot` には入れない（URL は確かめるためのもので、金額の計算には使わない）
- DB: `routes` の表に URL の列（NULL 可）を足すマイグレーション。**DB のスキーマの変更なので、その PR もオーナーが確認する**
- backend: 経路検索のインターフェース（例: `RouteSearch`。出発駅・到着駅を受け、経路結果の URL と、分かれば運賃を返す）と、次の2つの実装
  - 駅すぱあとフリープランの実装。API のキーは backend の環境変数（`.env`。リポジトリには入れない）から読む。フロントにはキーを渡さない
  - キーが無いときの実装（「使えない」と返す）。CI・テスト・キーの無い環境では、こちらを使う
- API: 経路検索の受け口（例: `GET /api/route-search?from=…&to=…`）。駅名の入力の判定は、ほかの API と同じく受け口で行う
- frontend: ルートのフォームに「駅すぱあとで経路を見る」を置く。キーが無いときは出さない。URL の欄は手でも直せる
- テストでは、外部の API を呼ばない（fetch を差し替える。今の画面のテストと同じやり方）

## 影響

- 駅すぱあとフリープランの申し込みが要る（オーナーが行う。キーが届くまで3営業日ほど）。キーが届く前でも、キーが無いときの実装で、ほかの作業は進められる
- 出発地・到着地は今は自由な文字（例: 「自宅」）なので、経路検索には別に**駅名**を入れてもらう
- 外部のサービスに駅名を送ることになる（個人の情報は送らない）
- 教科書の題材: インターフェースと、実装の差し替え（依存性の注入）。Java の interface と比べる

## 実装の前に確かめること

- 駅すぱあとフリープランの仕様書（`docs.ekispert.com/v1/le/`）で、使える API（簡易の経路探索で経路結果の URL が返るか）・1日の上限・表示の義務（「駅すぱあと」の表記など）・URL を保存してよいか
- 上の条件が合わなければ、この ADR を見直す（A だけにする、など）

## 見直すとき

- 運賃の数値も自動で入れたくなったとき → C か D を、新しい ADR で検討する（インターフェースはそのまま使える）
- 定期代（通勤定期）を扱うことになったとき → 定期代の計算がある C を検討する
